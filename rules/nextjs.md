# Next.js

Assumes the `react.md` rules in this same folder apply everywhere React itself is in play — this file only adds what's specific to Next.js (App Router, routing, metadata, server/client boundaries). Don't restate a `react.md` rule here; reference it.

## General

- App Router only. No `pages/` directory, no mixing routers.
- Every component is a Server Component by default. Add `"use client"` only where the component genuinely needs state, effects, event handlers, browser APIs, or a client-only library (Framer Motion, TanStack Query hooks).
- Business logic never lives in a `page.tsx`. A page composes UI and calls into the matching `domains/<domain>/` module — same domain split as the rest of the codebase (`trips`, `expenses`, `members`, `settlement`, `notifications`, `auth`).

## File-Type Destination Table

This is the canonical answer to "where does this file go" — don't improvise a new location.

| File type | Location | Notes |
|---|---|---|
| Route page | `app/(group)/segment/page.tsx` | One per route; UI composition only |
| Layout | `app/(group)/layout.tsx` | Shared chrome for everything under it |
| Loading UI | `app/(group)/segment/loading.tsx` | Required for any route with a non-trivial fetch |
| Error boundary | `app/(group)/segment/error.tsx` | Required per route; must be a Client Component |
| Route handler (API) | `app/api/<domain>/route.ts` | Mirrors the `domains/` split — don't group by HTTP verb, group by domain |
| Server Action | `domains/<domain>/actions.ts` | Never inline in a component file |
| Domain business logic | `domains/<domain>/*.ts` | Settlement math, split validation, balance aggregation, etc. |
| Zod schemas | `domains/<domain>/schemas.ts` | Same schema drives client form validation and server validation — one source, not two |
| shadcn/ui primitives | `components/ui/` | Generated by the shadcn CLI — don't hand-edit unless customizing a primitive project-wide |
| Shared app components | `components/` | Used by 2+ routes |
| Route-local components | `app/(group)/segment/_components/` | Single-use, never imported elsewhere |
| Route-local hooks | `app/(group)/segment/_hooks/` | Same rule as above |
| Shared hooks | `lib/hooks/` or `domains/<domain>/hooks/` | Domain-specific hook → domain folder; generic (e.g., `useDebounce`) → `lib/hooks/` |
| Cross-cutting clients | `lib/` | Supabase client, email client, analytics client |
| Prisma schema/migrations | `db/` | |
| Env schema + constants | `config/` | See Environment Variables below |
| Tests | `tests/`, mirroring `domains/` | Per the Tech Design's testing layout |

**Underscore-prefixed folders (`_components`, `_hooks`, `_lib`) are not routes.** Next.js excludes anything starting with `_` from routing — this is how you colocate route-local code without it accidentally becoming a URL segment. Anything reused across more than one route does not belong under an `_` folder; promote it to `components/`, `lib/`, or the owning `domains/` folder instead.

## Routing

- Route groups (`(marketing)`, `(auth)`, `(dashboard)`) organize without affecting the URL — use them to scope layouts and metadata defaults per section, exactly as laid out in the Tech Design's project structure. Don't invent a fourth group without a reason.
- Dynamic segments (`[id]`) only where the PRD's data model actually requires one (`groups/[id]`). Don't add a catch-all (`[...slug]`) unless a real feature needs it — none does at MVP.
- A route segment folder must contain a `page.tsx` (or be a pure layout wrapper) to be a real route. A folder with only components in it is not a route — put those components under `_components/` so the folder can't be mistaken for one.

## Server vs. Client Components

- Push `"use client"` as far down the tree as possible — wrap the interactive leaf (a form, a dropdown, a button with an `onClick`), never the page or the layout around it.
- Never fetch initial page data with `useEffect` + `fetch` in a Client Component when the Server Component above it could fetch directly and pass the result down as props. This is the Next.js-specific case of the `react.md` Effects rule ("`useEffect` only to synchronize with external systems") — initial data for a page isn't synchronizing with anything, it's just data the server already has.

```tsx
// Bad — client-side fetch for data the server already had.
"use client";
export function GroupBalances({ groupId }: { groupId: string }) {
  const [balances, setBalances] = useState(null);
  useEffect(() => {
    fetch(`/api/groups/${groupId}/balances`).then(r => r.json()).then(setBalances);
  }, [groupId]);
  ...
}

// Good — Server Component fetches directly; only the interactive part is a client boundary.
export async function GroupBalancesPage({ params }: { params: { id: string } }) {
  const balances = await getBalances(params.id); // domains/settlement
  return <BalancesView initialBalances={balances} />; // client component, hydrates from props
}
```

## Data Fetching

- Server Components: call the domain function or Prisma directly. No loading spinner needed for the initial paint — that's what `loading.tsx` is for if the fetch is slow.
- Client-side fetching/mutation after the initial load: TanStack Query only, per the Tech Design. Never a raw `fetch` + `useState`/`useEffect` combo in a Client Component.
- Server Actions handle form-style mutations. Route Handlers exist for anything needing a stable contract a client-side `useMutation` calls, or for webhooks.
- After a Server Action mutates data, call `revalidatePath`/`revalidateTag` so the UI reflects the change — don't rely on the client to manually refetch.
- Be explicit about cache intent on every `fetch` call rather than trusting the implicit default. Anything balance-related uses `{ cache: 'no-store' }` — a stale balance is worse than a cache miss.

## Metadata

- Every real page exports `metadata` (static) or `generateMetadata()` (when title/description depends on dynamic data, e.g. a group's name). No hand-written `<title>`/`<meta>` tags in JSX — always the Metadata API.
- Set `title.template` once in the root layout so child pages provide only their own segment, not the full brand string every time.
- Public marketing pages (`(marketing)` route group): full metadata, including OpenGraph and Twitter card fields, using the OG image asset from the brand setup.
- Authenticated app routes (`(dashboard)` route group): set `robots: { index: false, follow: false }` on the group's layout — this is the PRD's "authenticated routes should be noindex" requirement, enforced at the layout level so no individual page can forget it.
- A dynamic route's metadata must never leak private data — don't put a group's balance or member names in a `<title>` that a link preview could expose.

## Loading & Error States

- Any route segment with a non-trivial fetch gets a `loading.tsx` built from the shadcn `Skeleton` component, shaped like the real content it's replacing — not a generic spinner.
- Every route segment gets an `error.tsx` (Client Component, per the Next.js requirement) with a way to retry, not just an apology message.
- `app/global-error.tsx` exists as the last-resort catch-all. Easy to forget, required.

## Middleware & Auth

- `middleware.ts` at the project root handles Supabase session refresh on every request and route protection (redirect unauthenticated users away from `(dashboard)` routes). Keep it to exactly that — session refresh and route gating. Anything more (analytics, feature flags, business logic) does not belong in middleware.

## Images & Fonts

- Always `next/image`. Never a raw `<img>` — it skips automatic sizing/optimization and reintroduces layout shift the framework already solves.
- Always `next/font`, loaded once in the root layout (Inter, per the design system). Never a Google Fonts `<link>` tag, never an `@import` in CSS.

## Environment Variables

- Never call `process.env.SOMETHING` directly outside `config/env.ts`. Validate the full set with Zod at startup so a missing variable fails loudly at build/boot, not silently three features deep at runtime.
- `NEXT_PUBLIC_` only for values genuinely safe in the browser bundle. Never a Supabase service-role key, database URL, or a Resend/PostHog secret key — those stay server-only.

## Anti-Patterns

- Never `"use client"` at the top of the root `layout.tsx`.
- Never fetch the same data in both a Server Component and a Client Component below it "just in case."
- Never put settlement math, split validation, or any other business rule directly in a `page.tsx` — it lives in `domains/`.
- Never let a folder without a `page.tsx` sit inside a route group as if it were a route — use `_components`/`_hooks` for anything that isn't meant to be navigable.
